# CLAUDE.md — ЭНЭКА.Командировки

Приложение в Microsoft Teams: заявки на командировки и бронирование служебных автомобилей.

> **Источник требований:** `docs/source/ЭНЭКА.Командировки.md` (концепция) и
> `docs/source/ЭНЭКА.Командировки. Этап 1.md` (состав этапа 1, экраны Э1–Э9,
> карточки К1–К16, сообщения Т1–Т6). Это спецификация — читать перед задачей,
> не придумывать поведение заново.
>
> **Текущий план и статус:** `docs/plan.md`

## Стек

- **Next.js 16** (App Router) — вкладка Teams, Server Actions, вебхуки ботов
- **React 19**, TypeScript 5 (строгий, `any` запрещён), Tailwind CSS 4
- **Supabase** (Postgres) — база данных; доступ только с сервера через `service_role`
- **botbuilder 4** — Teams-бот (Bot Framework)
- **grammy** — Telegram-бот водителей
- **jose** — проверка токенов Entra ID
- **Zod** — валидация входных данных на сервере
- **lucide-react** — иконки

## Архитектура

Размещение повторяет схему геймификации: приложение на Vercel, работа по
расписанию — на VPS.

```
Вкладка Teams ─┐
Бот Teams ─────┼─→ Next.js на Vercel ─→ Supabase (Postgres)
Бот Telegram ──┘                            ↑
                   Воркер на VPS в Docker ──┘
                   (планировщик, опрос раз в минуту;
                    синхронизация сотрудников из Graph)
```

- Один Next.js-проект обслуживает вкладку, `/api/messages` (Teams) и `/api/telegram`.
  Публичный HTTPS-адрес даёт Vercel, отдельный домен для запуска не нужен.
- На Vercel нет постоянно работающего процесса, поэтому **любая работа по времени —
  только в воркере на VPS**. В route handlers и Server Actions таймеров не создавать:
  функция завершается сразу после ответа.
- Воркер читает таблицу `notifications` и отправляет то, у чего наступил `send_after`.
  Все отложенные и повторяющиеся сообщения ставятся в `notifications` с `dedupe_key`,
  поэтому планировщик идемпотентен и переживает перезапуск.
- Вкладка в Teams должна открываться с production-адреса Vercel. У preview-деплоев
  адрес другой, и вход через Entra ID на них не работает.

## Вход и права

- Вход — Entra ID SSO: вкладка получает токен через `teams-js getAuthToken()`,
  сервер проверяет его в `@/lib/auth/verifyTeamsToken`.
- Роли (`aho`, `reception`, `finance`) хранятся в таблице `employee_roles`
  и назначаются АХО в приложении, **не** через App Roles в Entra.
- Supabase Auth и RLS не используются: доступ проверяется на сервере по роли.
  Поэтому любой запрос к данным идёт через Server Action или route handler,
  никогда напрямую из клиентского компонента.
- Справочник сотрудников — локальная копия из Microsoft Graph (таблица `employees`),
  синхронизируется воркером. На каждый запрос в Graph не ходим.

## Правила кода

- Алиас `@/` → `src/`. Относительные пути только внутри модуля.
- Порядок импортов: React/Next → сторонние → `@/…` → локальные → `import type` последними.
- Только функциональные компоненты. Props через `interface`. Один компонент — один файл.
- Server Components по умолчанию. `'use client'` — как можно глубже в дереве.
- Server Actions в `src/modules/<name>/actions.ts` (`'use server'`), возвращают
  `{ success: true, data: T } | { success: false, error: string }`.
- Входные данные Server Actions валидируются через Zod `safeParse`.
- После мутации — `revalidatePath`/`revalidateTag`.
- Цвета и отступы — Tailwind-классы. Произвольные HEX в классах не использовать.
- Комментарии — по-русски и только там, где логика неочевидна.
- UI и тексты сообщений — русский язык; код — английский.

## Структура

```
src/
  app/              # роуты вкладки и вебхуки ботов
  components/       # общие UI-компоненты
  modules/          # бизнес-модули: trips, cars, drivers, documents, reception
  lib/              # auth, bots, утилиты, общие типы
  config/           # env, supabase, константы приложения
worker/             # планировщик и синхронизация Graph — деплоится на VPS, не на Vercel
supabase/migrations # схема БД
teams/              # манифест приложения Teams
docs/               # документация и план; docs/source — исходные требования
scripts/            # вспомогательные скрипты
```

## Инварианты, которые нельзя нарушать

Они заданы требованиями и закреплены в схеме БД — не обходить их в коде:

- Двойная бронь невозможна: ограничения `trips_car_no_overlap` и
  `trips_driver_no_overlap` (EXCLUDE в Postgres), а не проверка в интерфейсе.
- Между бронями одного автомобиля — не менее 10 минут (`fn_booking_buffer()`).
  После фактического возврата буфер считается от него, а не от планового времени.
- Поездку нельзя закрыть без показания одометра.
- Следующую выдачу машины нельзя оформить, пока не закрыта предыдущая поездка.
- Начальное показание одометра = значение при прошлом возврате (`cars.odometer_km`),
  снимок сохраняется в `trips.odometer_start_km` при выдаче ключей.
- Исправление одометра после закрытия сохраняет прежнее значение, причину и автора
  (`odometer_readings`), значения последующих поездок автоматически не меняются.
- Перенос и отмена доступны только до выдачи ключей; вне своей заявки — только АХО.
- Любое изменение заявки пишется в `trip_events` (журнал в Э3).
- Изменение данных заявки снимает отметку «Документы готовы»
  (`docs_recheck_required`), финотдел проверяет повторно.

## Чего не делать

- Не добавлять зависимости без запроса.
- Не расширять объём: PDF, путевые листы, топливо, зарубежные поездки, 1С,
  согласование руководителем — вне этапа 1.
- Не использовать `Action.Execute` в адаптивных карточках: ответ на invoke
  через `processActivityDirect` не возвращается. Кнопки — `Action.Submit`.
- Не хранить серверные данные в `useState`.
- Не держать таймеры в веб-процессе.
