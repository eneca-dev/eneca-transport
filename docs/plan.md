## Принятые решения

| Вопрос | Решение |
|---|---|
| Хранение данных (вариант А/Б, раздел 8) | **А.** Отдельный проект Supabase |
| Роли АХО / Рецепция / Финотдел | В своей БД (`employee_roles`), назначает АХО. Не App Roles в Entra — иначе каждое назначение роли блокируется заявкой в ИТ |
| Размещение | Приложение на **Vercel** (команда `development-depts-projects`), тариф Pro |
| Навигация по разделам | Закладкой Teams рядом с «Чат» объявлены только «Мои поездки» — экран, доступный всем. Служебные разделы (Машины, Водители, Рецепция, Документы, Календарь) живут внутри вкладки и показываются по роли. Манифест не умеет скрывать закладку от части сотрудников: что объявлено — увидят все 900, и большинству закладка выдала бы отказ. Полоска разделов внутри вкладки не рисуется вовсе, если у человека один раздел: его название Teams уже показывает закладкой |
| Оформление | Палитра Fluent 2, тема берётся у Teams (`app.getContext().app.theme`) и подменяется на ходу. Светлая, тёмная и высококонтрастная; стеклянная показывается как светлая. Цвета — токены в `src/app/globals.css`, в компонентах ни HEX, ни вариантов `dark:`. Шрифт системный Segoe UI, без запроса к Google Fonts |
| Где живёт планировщик | **Vercel Cron, решено 19.11.** На тарифе Pro задача запускается раз в минуту, что буквально покрывает требование спецификации «проверка подтверждений — не реже раза в минуту». Отдельный сервер не даёт здесь ничего: проход идемпотентен, состояние целиком в базе, а секрет задачи Vercel передаёт сам. ВПС был в первоначальном плане по аналогии с соседним проектом, а не из нужд этого. Задачи: `/api/jobs/tick` раз в минуту, `/api/jobs/sync-employees` раз в сутки |
| Публичный адрес | Постоянный адрес даёт Vercel, домен от ИТ для запуска не нужен. Задан одной переменной `NEXT_PUBLIC_APP_DOMAIN`. Корпоративный поддомен добавляется позже в Vercel → Domains: Vercel выдаёт готовую DNS-запись, её и передаём ИТ |
| Справочник сотрудников | Локальная копия из Microsoft Graph (application-разрешение `User.Read.All` + синхронизация по расписанию), без on-behalf-of |
| Регистрация в Entra | Одна регистрация на вкладку и бота. App ID URI — `api://<домен>/botid-<client-id>` |
| Регистрация бота | **Teams Developer Portal**, без ресурсов Azure. Подписки и платёжного аккаунта в тенанте нет, а Azure Bot дал бы только тип Single Tenant и лишние каналы связи. Следствия: тип приложения бота — Multi tenant, идентификатор отдельный от вкладки |
| Права в Entra ID | Каталожная роль не нужна: достаточно быть **владельцем (Owner)** регистраций приложения. `Application Developer` — только если в тенанте запрещена самостоятельная регистрация приложений. Согласие администратора требуется однократно и только на application-разрешение `User.Read.All` |

## Стиль коммитов

Одна строка: `<область>: <что сделано>`. Со строчной буквы, без точки в конце,
до 72 знаков. Тело добавляется, только когда в коммите несколько несвязанных
изменений, — списком через `-`.

Области:

| Область | Когда |
|---|---|
| `feat` | новая возможность приложения: экран, справочник, сценарий |
| `fix` | исправление того, что уже было и работало неправильно |
| `infra` | окружение, деплой, вебхуки, проверочные скрипты |
| `chore` | уборка: удаление временного, переименования, зависимости |
| `docs` | только документация и план |

Номера инкрементов (`И1`, `И2`) в коммиты не выносятся: инкремент — это
единица плана, а не изменения. Какому инкременту относится работа, видно
по `docs/plan.md`.

```
feat: справочник машин и водителей
feat: заявка на поездку и бронь без водителя
fix: буфер 10 минут считается от фактического возврата
docs: уточнён порядок регистрации в Entra
```

## Что уже сделано

- Каркас Next.js 16 + TypeScript + Tailwind 4.
- Схема БД: `supabase/migrations/0001_init.sql` — сотрудники, роли, машины, ремонты,
  водители, недоступность, коды привязки Telegram, поездки с ограничениями
  непересечения броней, история одометра, журнал поездки, очередь сообщений.
- Проверка входа Entra ID: вкладка `/` → `/api/auth/me`.
- Эхо-вебхуки `/api/messages` (Teams) и `/api/telegram` для проверки связи.
- Сборка пакета Teams: `npm run teams:package`.
- Синхронизация сотрудников из Graph: `POST /api/jobs/sync-employees`
  Запускается Vercel Cron раз в сутки, вручную — тем же адресом с `CRON_SECRET`.
  Берутся все внутренние учётные записи (`userType eq 'Member'`), уволенные
  остаются в базе с `is_active = false` — на них ссылаются закрытые поездки.
  Отделить служебные ящики от людей каталог ЭНЭКА не позволяет: 16.11 проверено,
  что ни отдел, ни должность, ни лицензия для этого не годятся.
- Роли: `scripts/grant-role.mjs`. Первого АХО назначить в интерфейсе неоткуда,
  поэтому он выдаётся скриптом; дальше роли раздаёт АХО в приложении.
- Вход во вкладку: токен Teams проверяется в каждом Server Action, роль читается
  из базы. Куки нет намеренно — вкладка живёт в iframe, и Safari с мобильным
  клиентом сторонние куки не отдают.
- Э8 «Машины»: список, добавление, правка, периоды ремонта.
- Э9 «Водители»: список, добавление, правка, удаление ошибочной записи, периоды
  недоступности с причиной, кнопка «Выдать код». Код гасится тем же запросом,
  которым проверяется, — одновременный ввод достанется только первому.
  Последствия недоступности по К13 (снятие с предстоящих поездок) появятся
  вместе с поездками в И2 — отмечать период уже можно, снимать пока нечего.
- Привязка Telegram: водитель вводит код боту `@eneca_trips_bot`, чат
  записывается в `drivers.telegram_chat_id`. Проверено 17.11 на живой базе:
  повторный ввод кода не срабатывает, пересекающиеся периоды недоступности
  отклоняются ограничением `23P01`, каскад чистит коды вместе с водителем.
- **Защита привязки (17.11, миграция `0002`).** Бот публичный: его находят
  поиском, поэтому код может вводить кто угодно. Четырёхзначный код из примера
  спецификации перебирается за минуты — всего 10 000 значений. Что меняется:
  код шестизначный; не больше 5 неудачных попыток на чат в час
  (`telegram_link_attempts`); привязка только в личной переписке, иначе
  назначения с фамилиями пассажиров ушли бы в групповой чат; в Э9 видно, кто
  подключился (`drivers.telegram_username`), чтобы АХО сверила глазами.
  Открытым остаётся не это, а допустимость Telegram для таких данных —
  вопрос Павлу Соколову ниже.
- Оформление следует теме Teams; палитра — токены в `src/app/globals.css`.
- Карточки Teams: К1 автору и К2 участникам уходят сразу из Server Action,
  запись об отправке ложится в `notifications` с `dedupe_key` и
  `external_message_id`. Адрес личного чата сохраняется в
  `teams_conversations` при установке приложения (`conversationUpdate`) и при
  любом сообщении боту.
- **Проверено 19.11 на живых людях.** К1 дошла автору, К2 — участнику, у
  которого приложение установлено. Участнику без приложения Bot Connector
  отвечает **403** «Bot is not installed in user's personal scope», а не 404,
  как можно ожидать по документации. Обрабатываются оба кода: для нас это
  один и тот же случай — писать некуда. Отправка при этом не роняет создание
  поездки, причина пишется в `notifications.last_error`.
- Кнопка «Открыть» в карточках ведёт во вкладку через глубокую ссылку Teams с
  номером поездки в `subEntityId`; вкладка читает его и открывает Э3.
- Э1, Э2 и Э3: список поездок, заявка в три шага, карточка поездки с журналом.
  Занятые машины и водители показываются с причиной и не выбираются; отказ
  базы на отправке возвращает к шагу 2. Участники — поиском по справочнику.
- Т1 водителю: сообщение с кнопками «Подтверждаю» и «Не могу», ответ приходит
  как `callback_query`. После ответа кнопки гасятся, повторное нажатие
  отсекается статусом. При отказе сразу уходит К14 всем сотрудникам АХО.
  **Проверено 19.11** поддельными нажатиями через настоящий вебхук: чужой чат
  за водителя ответить не может, мусор в кнопке ничего не меняет, повторное
  нажатие не переписывает ответ, К14 доставляется.
- К14 отправляется до правки сообщения в Telegram намеренно: по требованиям
  она уходит сразу после «Не могу», и отказ Telegram на гашении кнопок не
  должен оставить АХО без уведомления.
- Форматирование даты и времени — одним набором в `src/lib/datetime.ts`.
  До этого оно расползлось по девяти файлам, и русская локаль ставила запятую
  между датой и временем: «25.11, 07:00 – 26.11, 19:00» читается хуже.
- Планировщик `/api/jobs/tick` на Vercel Cron, раз в минуту. Проверяет сроки:
  вышли ли 15 минут на подтверждение (Т2 водителю, К14 в АХО) и наступило ли
  время выезда без подтверждённого водителя (К16 автору).
- **Ключ занимается до отправки, а не после.** Разница существенная: карточку
  по событию можно записать после отправки — событие одно. Карточку по сроку
  планировщик встречает каждую минуту, и при записи после отправки автор
  получил бы К16 шестьдесят раз в час. Весь журнал отправок переведён на один
  порядок: занять ключ, отправить, отметить (`modules/notifications/outbox`).
- Кнопки карточек Teams: `Action.Submit` приходит обычным сообщением с
  заполненным `value`, а `replyToId` указывает на карточку — по нему она
  перерисовывается в итог, и повторно нажать нечего. Право на действие
  проверяется по Entra OID нажавшего, а не по тому, кому карточка
  отправлена: карточку можно переслать.
- К16 даёт автору два решения: «Поеду сам» (назначение водителя снимается,
  бронь остаётся, документы — на повторную проверку) и «Отменить поездку»
  (освобождение брони триггером базы). Отмена до выдачи ключей, как в
  требованиях.
- **Проверено 19.11** на живой базе через настоящую задачу: просроченное
  назначение переводится в `timeout`, свежее не трогается, Т2 и К14
  записываются, повторный проход не дублирует; К16 уходит один раз, сколько
  бы раз планировщик ни запускался.
- Проверка доступов: `scripts/check-env.mjs` (формат переменных) и
  `scripts/check-access.mjs` (живые запросы в Entra, Graph, Bot Connector,
  Supabase, Telegram). Значения секретов не печатают.

## И0. Доступы и проверка связи — делается вручную

Это критический путь: пока не пройдено, ни бот, ни вкладка не проверяются.

### 1. Деплой на Vercel — делается первым, он даёт адрес

Адрес нужен раньше всего: он зашивается в App ID URI в Entra, в messaging endpoint
бота и в манифест Teams. Поэтому сначала деплой, потом регистрации.

1. Запушить код в `eneca-dev/eneca-transport`.
2. `vercel.com` → команда `development-depts-projects` → Add New → **Project** →
   Import Git Repository → `eneca-dev/eneca-transport`. Если репозиторий приватный,
   Vercel попросит доступ к организации на GitHub.
3. Framework Next.js определится сам, Root Directory — корень.
4. Deploy. Переменные окружения добавляются после — на первом деплое их ещё нет.

Проект в Vercel назван `eneca-trips`, production-адрес — `eneca-trips.vercel.app`.
Это значение `NEXT_PUBLIC_APP_DOMAIN`, без схемы и в нижнем регистре. Адреса
preview-деплоев не использовать: они меняются, и вход через Entra на них не работает.
Деплой запускается пушем в `main`.

### 1а. Корпоративный поддомен `trips.eneca.by` — готов

**11.11:** запись в зоне создана системным администратором, домен работает.
`NEXT_PUBLIC_APP_DOMAIN=trips.eneca.by` — именно он идёт в App ID URI,
в messaging endpoint бота и в манифест Teams. Адрес `eneca-trips.vercel.app`
остаётся как запасной, но нигде не прописывается.

В зоне: `trips` → `CNAME` → `391d08247d32abd4.vercel-dns-016.com.`
Зона `eneca.by` живёт на `ns1.hoster.by`, правится только системным
администратором, записей CAA в ней нет — выпуск сертификата ничто не ограничивает.

Грабли на будущее: панель hoster.by дописывает имя зоны к значению, если оно
введено как относительное имя. С первого раза запись встала как
`...vercel-dns-016.com.eneca.by` и не работала.

Домен лучше адреса Vercel и его стоит взять до регистрации в Entra: домен
попадает в App ID URI, в messaging endpoint бота и в манифест Teams, поэтому
смена задним числом означает переделку всех трёх мест.

Что выяснено:

- Зона `eneca.by` обслуживается `ns1.hoster.by` / `ns2.hoster.by` — DNS правится
  в панели **hoster.by**. Апекс `eneca.by` указывает на `178.172.235.206`
  (корпоративный сайт), почта там же — посторонние записи не трогать.
- Домен `eneca.by` уже привязан к команде Vercel, но nameservers третьей стороны,
  то есть Vercel зоной не управляет. Wildcard `*.eneca.by` в зоне нет.
- `gamification.eneca.by` — CNAME на `500be54d73d66958.vercel-dns-016.com`.
  Значение уникально для каждого домена: копировать его для `trips` нельзя,
  Vercel выдаёт свой адрес вида `<хеш>.vercel-dns-0XX.com`.
- Сотрудник, заводивший `gamification.eneca.by`, уволился. Доступ в hoster.by
  искать в ИТ (там же корпоративный сайт) либо восстанавливать через поддержку
  hoster.by по договору.

Порядок: Vercel → проект → Settings → Domains → Add Domain → `trips.eneca.by`
(подтверждение владения не потребуется, домен уже в команде) → скопировать
показанное значение CNAME → в hoster.by добавить запись `CNAME` с именем `trips`
и этим значением, TTL по умолчанию. Vercel сам переключит статус на Valid
и выпустит сертификат.

### 3. Регистрация приложения в Entra ID

`entra.microsoft.com` → App registrations → New registration:

- Имя: `ЭНЭКА.Командировки`, тип — **Accounts in this organizational directory only**,
  Redirect URI не нужен.
- Записать **Application (client) ID** и **Directory (tenant) ID**.
- **Manage → Manifest**: `requestedAccessTokenVersion` = `2`.
  Делать **до** следующего шага, порядок принципиален. В тенанте, скорее всего,
  включена политика, запрещающая произвольные домены в Application ID URI
  («All newly added URIs must contain a tenant verified domain, tenant ID, or app ID»).
  Адрес на `vercel.app` под неё не подходит, но приложения с v2-токенами
  от этой политики освобождены. Если сначала задать URI, Entra его отклонит.
- **Expose an API → Application ID URI**: `api://<домен>/botid-<client-id>`
  (именно `botid-`, потому что в приложении есть и бот, и вкладка).
  Если URI всё равно отклонён — значит нужен корпоративный поддомен
  (он верифицирован в тенанте) либо исключение для приложения от админа.
- **Add a scope**: имя `access_as_user`, кто может соглашаться — **Admins and users**,
  отображаемые имена и описания заполнить по-русски.
- **Authorized client applications** — добавить оба ID, иначе SSO молча не работает:
  - `1fec8e78-bce4-4aaf-ab1b-5451cc387264` — Teams desktop и mobile
  - `5e3ce6c0-2b1f-4285-8d4b-75ee78787346` — Teams web
- **API permissions → Microsoft Graph**:
  - delegated: `openid`, `profile`, `email`, `offline_access`, `User.Read`
  - application: `User.Read.All` — для синхронизации справочника сотрудников
  - application: `TeamsAppInstallation.ReadWriteSelfForUser.All` — чтобы ставить
    приложение сотруднику, который боту не писал (см. ниже). Узкое: позволяет
    управлять только собственной установкой приложения
  - нажать **Grant admin consent**
- **Certificates & secrets** → новый client secret, записать значение сразу.

### 4. Регистрация бота

Бот заводится в **Teams Developer Portal** (`dev.teams.microsoft.com` → Tools →
Bot management). Портал сам создаёт регистрацию в Bot Framework, подписка Azure
для этого не нужна.

- **Configure → Delivery method**: HTTPS endpoint,
  адрес `https://trips.eneca.by/api/messages`
- **Channels**: включить Microsoft Teams
- **Client secrets**: создать, значение записать сразу

**12.11: решение — подписку Azure не запрашиваем.** В тенанте нет ни подписок,
ни платёжного аккаунта, то есть подписка — не клик администратора, а финансовый
процесс в организации. Ресурс Azure Bot (F0) бесплатен, но даёт только тип
приложения Single Tenant, управление в портале Azure и дополнительные каналы
связи — ничего из этого в этапе 1 не нужно. Заявка на подписку отозвана.

**Прецедент в организации.** Бот протоколов встреч **EnecaProtocolMeetBot**
(репозиторий `eneca-dev/Eneca_AI_bot`, работает на VPS за `ai-bot.eneca.work`)
отправляет протокол в чат Teams сам, без Azure. Схема в
`services/teams_sender.py` — та же, что у нас: ссылка на разговор сохраняется при
первом сообщении, затем токен по `client_credentials` со областью
`https://api.botframework.com/.default` и POST активности в Bot Connector.
Значит исходящая отправка в этом тенанте работает и подписка для неё не нужна.
Его регистрацию переиспользовать нельзя: messaging endpoint у регистрации один,
и он занят.

Если отправка сообщений ботом всё-таки упрётся в 401 — возвращаемся к ИТ с
конкретной ошибкой, а не с общей просьбой. Параметры ресурса на этот случай:
тип **Single Tenant**, существующая регистрация `eneca.trips`, SKU **F0**,
messaging endpoint `https://trips.eneca.by/api/messages`, канал Microsoft Teams.
Штатный путь перехода — кнопка **Migrate** в Bot Framework Portal: она создаёт
ресурс Azure Bot на той же регистрации.

Личную пробную подписку с кредитом 200 долларов не использовать: нужна привязка
личной карты, а продакшен-ресурс оказывается в подписке, которой организация не
управляет, и умирает вместе с ней через 12 месяцев.

**16.11: бот не зарегистрирован в Bot Framework Service — не работают обе
стороны.** Приложение установлено в Teams, вкладка и бот Telegram проверены,
а бот Teams молчит и на входящее, и на исходящее.

Исходящее: `POST /v3/conversations` → 401 `Authorization has been denied for
this request` во всех четырёх регионах (`amer`, `emea`, `apac`, `india`).
Запрос к заведомо несуществующему чату даёт тоже 401, а не 404 — значит отказ
происходит на слое аутентификации, до поиска ресурса, и от тела запроса не
зависит (проверены оба формата `bot.id`: с префиксом `28:` и без). Токен при
этом корректен: `aud` = `https://api.botframework.com`, `appid` = id бота,
издатель — тенант `botframework.com` (`d6d49420-…`). То есть пара id/секрет
верная и тип multi-tenant подтверждён: single-tenant регистрация такой токен
не получила бы вовсе.

Входящее: `/api/messages` отвечает 401 на неподписанный запрос и 400 на битый
JSON, то есть маршрут исправен и его просто никто не вызвал.

Обе стороны отказывают одной причиной: коннектор не признаёт бота. Проверка
доступов этого не поймала — `scripts/check-access.mjs` брал токен, но не делал
ни одного вызова к Bot Connector. Исправить: добавить в него реальный вызов.

**Ошибка в рассуждении 12.11.** Из того, что `services/teams_sender.py` у бота
протоколов не обращается к Azure, не следует, что у его регистрации нет ресурса
Azure Bot: из кода ресурс не виден вообще — он живёт в подписке, а в коде
остаются только app id и секрет. Прецедент доказывает, что исходящая отправка в
этом тенанте работает, но не доказывает, что она работает без Azure. Вывод
«подписка не нужна» был сделан из наблюдения, которое его не подтверждает.

**16.11, вечер: причина установлена точно — входящее работает, исходящее нет.**
Проверено после того, как маршрут начал писать входящие запросы в таблицу
`debug_inbound` (логи Vercel на этом проекте пусты даже для запросов, которые
заведомо обработаны функцией).

Что показала запись настоящего сообщения из Teams:

- Teams доставляет активность на `https://trips.eneca.by/api/messages`;
- подпись сходится, `processActivityDirect` активность принимает;
- падение происходит дальше, на `context.sendActivity` — `RestError:
  Authorization has been denied for this request` из HTTP-клиента Azure.
  Это другая ошибка, чем у неподписанного запроса (`Unauthorized Access.
  Request is not authorized`, локальная проверка), и именно она отличает
  «не дошло» от «дошло, но не можем ответить».

Настоящий `serviceUrl` тенанта содержит его идентификатор в пути:
`https://smba.trafficmanager.net/emea/41066eec-…/`. Отправка в этот адрес, в
реальный `conversation id`, выданный самим Teams, тоже даёт 401. То есть два
независимых пути — адаптер botbuilder на Vercel и скрипт на голом `fetch` —
отвергаются одинаково.

**Причина — центр выдачи токена, а не Azure.** Bot Connector принимает только
токен, выданный тенантом ЭНЭКА, а мы брали его у `botframework.com`:

| центр выдачи | отправка в чат |
|---|---|
| `login.microsoftonline.com/botframework.com` | 401 Authorization has been denied |
| `login.microsoftonline.com/41066eec-…` | **201 Created** |

Токены в обоих случаях валидны и имеют `aud = https://api.botframework.com`,
различается только издатель. Developer Portal показывает бота как MultiTenant,
и это сбивает с толку: по отношению к Bot Connector он ведёт себя как
**SingleTenant**. Отсюда правило в `.env.example` и проверка в
`scripts/check-env.mjs`: `MICROSOFT_APP_TYPE=SingleTenant` и обязательный
`MICROSOFT_APP_TENANT_ID`.

Подписка Azure и ресурс Azure Bot не нужны. Решение 12.11 остаётся в силе,
отменяется лишь вывод, сделанный днём 16.11.

Найдено по исходникам бота протоколов (`eneca-dev/Eneca_AI_bot`, публичный):
в `services/teams_sender.py` строка `tenant = settings.tenant_id or
"botframework.com"` — у них `TENANT_ID` задан, поэтому их бот всегда брал
токен у тенанта и проблемы не знал.

Проверено после смены типа: бот отвечает на сообщение; бот создаёт личный чат
по Entra OID и пишет первым (`scripts/teams-proactive-test.mjs --oid`);
`scripts/check-access.mjs` даёт 403 вместо 401 на несуществующий чат, то есть
коннектор бота признаёт.

Настоящий `serviceUrl` тенанта — `https://smba.trafficmanager.net/emea/41066eec-…/`,
но и базовый `…/emea/` без тенанта работает: тенант в пути на результат не влиял.

Заодно отброшено по дороге, чтобы не проверять повторно: канал Microsoft Teams
в портале включён; endpoint заполнен; секрет верный; регион ни при чём (401 был
во всех четырёх); `governmentChannelValidation_ValidateIdentity` в стеке — не
признак государственного облака, эта функция вызывается и на публичном пути;
домен привязан к тому же проекту Vercel, второго проекта нет.


Что нужно помнить про регистрацию из Developer Portal:

- Портал создаёт боту **свою** регистрацию приложения, идентификатор не совпадает
  с регистрацией вкладки. Поэтому в манифесте `botId` вынесен в отдельную
  переменную `NEXT_PUBLIC_TEAMS_BOT_ID`.
- Портал показывает тип **Multi tenant** и менять его не даёт, но для Bot
  Connector бот — **SingleTenant**: `MICROSOFT_APP_TYPE=SingleTenant` и
  `MICROSOFT_APP_TENANT_ID` = тенант ЭНЭКА. При MultiTenant входящие работают,
  а исходящие получают 401 — см. разбор 16.11 выше. Написанному в портале
  здесь верить нельзя, проверяется только запросом.
- Разрешений Microsoft Graph эта регистрация не запрашивает и согласия
  администратора не требует: сотрудник определяется по данным активности Teams.

Сами проактивные сообщения от способа регистрации не зависят: для отправки нужны
app id и secret, включённый канал Teams, сохранённый `conversation reference`
(поэтому приложение должно быть установлено сотруднику) и `serviceUrl` из
входящей активности. Bot Connector в цепочке есть всегда — Teams не доставляет
сообщения на наш сервер напрямую, и это не предмет выбора.

### 4а. Как бот пишет тому, кто ему не писал

Бот не может отправить сообщение в пустоту: пока приложение не установлено
сотруднику, разговора не существует и адреса для отправки нет. А участников
поездки добавляет АХО, и сами они боту не пишут — значит одного «сотрудник
написал первым» недостаточно.

Штатное решение — установить приложение программно:

```
POST https://graph.microsoft.com/v1.0/users/{entra-oid}/teamwork/installedApps
```

После установки Teams присылает боту событие установки с ссылкой на разговор, она
сохраняется в `teams_conversations`, дальше отправка обычная. Если у сотрудника
Teams запущен, установка происходит сразу.

Условия:

- разрешение приложения `TeamsAppInstallation.ReadWriteSelfForUser.All`;
- приложение должно быть **опубликовано в каталоге организации** — Graph ставит
  только то, что есть в каталоге. Это делает ИТ, и теперь это не удобство,
  а обязательное условие работы уведомлений.

**16.11: проверено на живом человеке.** Владимир Нестерович установил
приложение себе и боту не писал. Бот создал личный чат запросом
`POST /v3/conversations` по его Entra OID и отправил сообщение — оно дошло.
Значит установки приложения достаточно, входящее сообщение от сотрудника не
нужно. Непроверенным остаётся только случай «приложение не установлено»: там
по-прежнему нужны каталог организации и Graph.

Проще и надёжнее для запуска на всю компанию — **политика автоустановки**
приложения для группы сотрудников (тоже ИТ, однократно): тогда приложение стоит
у всех заранее и Graph нужен только для тех, кто в группу не попал.

Следствие для кода (И2): очередь `notifications` должна уметь состояние
«сначала поставить приложение, потом отправить». Схема не меняется — задача
`/api/jobs/tick` ставит приложение и переносит отправку через `send_after`.

Переход на Azure Bot, если он когда-нибудь понадобится: две переменные окружения
(`MICROSOFT_APP_*`, `NEXT_PUBLIC_TEAMS_BOT_ID`), пересборка манифеста и повторная
загрузка приложения в Teams. Код не меняется.

обработчика. Локально не воспроизводилось — Node 22 такое сочетание разрешает.

`package.json`, причина и условие снятия записаны там же. Путь «убрать
`botbuilder` из `serverExternalPackages`, пусть Next бандлит» проверен и закрыт:
сборка падает на `powershell-utils`, который приходит через `@azure/identity`.

Вывод на будущее: зелёный деплой в Vercel ничего не говорит о том, загрузится ли
серверный модуль. Проверять маршруты запросом, а не статусом сборки.

### Сколько это по срокам

До 30.11 — восемь рабочих дней, считая сегодняшний. Разложено так, что сначала
готов сквозной путь: от заявки до закрытой поездки с пробегом. Календарь,
история и исправление одометра после закрытия идут последними, потому что без
них пилот начать можно, а без выдачи ключей — нет.

Это не значит, что они необязательные: в требованиях они в обязательном списке.
Это значит, что при любой задержке первыми не успеют именно они.

Сначала сквозной путь поездки, боковые сценарии — после. Если сроки поджимают,

**Что получается к 30.11.** Сквозной путь целиком: заявка, бронь, водитель с
подтверждением, документы, выдача ключей, возврат с одометром, закрытие с
пробегом, напоминания, перенос и отмена. Пилот на этом работает.

**Что не успевает.** Календарь Э6, история Э7 и исправление одометра после
закрытия — 1–2 декабря, то есть в первые дни пилота. Они в обязательном списке
требований, и это надо сказать заказчику, а не умолчать. До них у АХО остаются
Э1, Э3 и справочники: занятость видно по карточкам поездок, просто не одной
таблицей.

**Чем можно вернуть эти два дня.** Работой в выходные 21–22 или 28–29.11. Это
решение не моё: скажешь — переложу сроки.

**Два изменения против прежнего порядка.**

Ветка «нужен водитель: да» входит в И2, а не откладывается. Ограничение базы
(`check (not needs_driver or status in ('draft','cancelled') or driver_id is not
null)`) запрещает только бронь «с водителем» без выбранного водителя — выбирать
при создании оно не мешает. Из всей ветки планировщик нужен единственному
пункту: напоминанию по молчанию через 15 минут. Выбор водителя, Т1, кнопки
«Подтверждаю» и «Не могу», К14 при отказе — всё это события и работают сразу.

Планировщик поднят с пятого места на третье. На нём висят Т2, К14 по молчанию,
К16 и все напоминания — пока его нет, в каждом следующем инкременте остаётся
долг. Сам он небольшой: таблица `notifications` с `send_after` и
`dedupe_key` уже есть, нужен обработчик и решение о размещении.

**Про 30.11.** Это не наша оценка, а дата из требований: «Целевой старт пилота —
30.11.2026, с учётом доступов ИТ и согласования с финотделом». До неё восемь
рабочих дней на семь инкрементов. Сквозной путь — заявка, документы, ключи,
возврат, закрытие, напоминания — в этот срок укладывается. Э6 и Э7 (календарь и
история) в него не укладываются и помечены как риск: они в обязательном списке
требований, но на них приходится последний день, и любая задержка съедает их
первыми. Своих предварительных условий дата тоже пока не выполнила: кто работает
от финотдела — неизвестно, доступы ИТ не получены.

После И4 сквозной путь уже проверяемый на реальных людях — это первая точка,
где можно показать результат АХО, не дожидаясь остального.

### Что внутри И2

Порядок такой, чтобы каждый шаг проверялся до того, как на него встанет
следующий.

1. **Доступность машин.** Запрос должен совпадать с ограничением базы до
   минуты. `booking_during` — это `[выезд, возврат + 10 минут)`, значит
   свободна та машина, у которой нет поездки, пересекающейся с таким же
   интервалом для новых дат. Проверяется на живой базе до того, как появится
   интерфейс: если запрос и ограничение разойдутся, экран предложит машину,
   которую база тут же отвергнет.
2. **Э2, три шага.** Бронь создаётся одной транзакцией, в `trip_events`
   пишется событие. Отказ `23P01` на третьем шаге — это не сбой, а штатный
   ход: он превращается в «Эту машину только что забронировали» и возврат к
   шагу 2, как требует спецификация.
3. **Э1.** Список своих поездок и тех, где человек участник.
4. **Э3.** Карточка поездки и журнал событий.
5. **К1 автору и К2 участникам.** Отправляются сразу в Server Action, не через
   планировщик: событие есть, ждать нечего.
6. **Водители.** Доступность водителя на шаге 2, назначение, Т1 с кнопками,
   обработка ответа, К14 Дарье при отказе. Проверяется на своём Telegram:
   настоящих водителей в справочнике пока нет.

**Решения, принятые по ходу.**

- Ветка «нужен водитель: да» работает в И2 целиком, кроме напоминания по
  молчанию. Свободным считается водитель, у которого нет пересекающейся брони
  (ограничение `trips_driver_no_overlap`) и нет периода недоступности на эти
  даты. После брони водителю сразу уходит Т1 с кнопками «Подтверждаю» и
  «Не могу»; отказ сразу даёт К14 Дарье. Не отвеченный Т1 до И3 оставляет
  поездку в состоянии «ожидается подтверждение» — это видно в Э3 и у АХО, но
  автоматического пинка через 15 минут пока нет.
- Кнопки в Telegram — inline-клавиатура, ответ приходит как `callback_query`.
  Это новый вид обновления в вебхуке, рядом с текстовыми сообщениями.
- Время вводится и показывается в минском. Минск круглый год UTC+3, перехода на
  летнее время с 2011 года нет, поэтому пересчёт однозначный. В базе —
  `timestamptz`.
- Участники выбираются поиском по справочнику, а не списком: 934 человека в
  выпадающий список не помещаются.

**Чем И2 может укусить.**

- Участник, у которого приложение не установлено, К2 не получит: Teams не даёт
  боту написать первым. До публикации в каталоге организации это остаётся, и на
  пилоте часть участников уведомлений не увидит. Тому, у кого приложение есть,
  бот пишет без проблем — проверено 16.11.
- Номер заявки (`#127`) выдаёт база через `generated always as identity`.
  Отменённые и черновики номера тоже съедают, так что нумерация будет с
  пропусками. Это нормально, но АХО стоит сказать заранее.

«Желательно» из раздела 1 (выгрузка в Excel, отчёт загрузки в процентах,
команда «Помощь») в этап 1 не планируется.

## Задачи ИТ перед запуском

Долгие по срокам, поэтому запрашиваются заранее, а не в последнюю неделю.
Для пилота на нескольких людях хватит загрузки приложения себе, но для
запуска на компанию нужны оба пункта.

1. **Публикация приложения в каталоге организации.** Без неё Graph не может
   установить приложение сотруднику, а значит уведомления не дойдут до тех, кто
   боту не писал.
2. **Политика автоустановки** приложения для группы сотрудников. Тогда
   приложение стоит у всех заранее.
3. **Согласие администратора** на два разрешения приложения: `User.Read.All`
   (выдано 11.11) и `TeamsAppInstallation.ReadWriteSelfForUser.All`.

## Что ещё ждём от заказчика

- **Список машин** (Дарья Шубина). На каждую: номер как в техпаспорте; модель;
  показание одометра с датой, когда оно снято; доступна ли машина для
  бронирования вообще; если сейчас в ремонте — с какой даты и что с ней.
  Одометр — единственное, что нельзя внести «примерно»: он становится начальным
  показанием первой поездки, и из него считается весь пробег дальше.
- **Список водителей** (Дарья Шубина). На каждого: фамилия и имя; телефон;
  есть ли Telegram и согласен ли водитель получать там рабочие сообщения.
  Без Telegram подтверждение поездки по Т1 работать не будет — это блокирует
  И6, поэтому ответ нужен раньше самих данных.
- **Кто от финотдела работает в приложении.** Нужно к И3 (24.11): очередь
  документов без человека, которому её показывать, проверить нельзя.
- **Согласие на передачу данных поездок через Telegram** (Павел Соколов).

- **Роль АХО для Дарьи Шубиной.** Выдаётся скриптом, нужна её рабочая почта.
  Без роли она не увидит ни справочников, ни календаря. К И4 (27.11), когда
  появится что показывать.
- Источник списка договоров: в этапе 1 — ручной ввод текстом, решено.
