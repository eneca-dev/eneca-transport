### 1. Деплой на Vercel — делается первым, он даёт адрес

Адрес нужен раньше всего: он зашивается в App ID URI в Entra, в messaging endpoint
бота и в манифест Teams. Поэтому сначала деплой, потом регистрации.

1. Запушить код в `eneca-dev/eneca-transport`.
2. `vercel.com` → команда `development-depts-projects` → Add New → **Project** →
   Import Git Repository → `eneca-dev/eneca-transport`. Если репозиторий приватный,
   Vercel попросит доступ к организации на GitHub.
3. Framework Next.js определится сам, Root Directory — корень.
4. Deploy. Переменные окружения добавляются после — на первом деплое их ещё нет.

Проект в Vercel назван `eneca-trips`, production-адрес — `eneca-trips.vercel.app`.
Это значение `NEXT_PUBLIC_APP_DOMAIN`, без схемы и в нижнем регистре. Адреса
preview-деплоев не использовать: они меняются, и вход через Entra на них не работает.
Деплой запускается пушем в `main`.

### 1а. Корпоративный поддомен `trips.eneca.by` — готов

**11.11:** запись в зоне создана системным администратором, домен работает.
`NEXT_PUBLIC_APP_DOMAIN=trips.eneca.by` — именно он идёт в App ID URI,
в messaging endpoint бота и в манифест Teams. Адрес `eneca-trips.vercel.app`
остаётся как запасной, но нигде не прописывается.

В зоне: `trips` → `CNAME` → `391d08247d32abd4.vercel-dns-016.com.`
Зона `eneca.by` живёт на `ns1.hoster.by`, правится только системным
администратором, записей CAA в ней нет — выпуск сертификата ничто не ограничивает.

Грабли на будущее: панель hoster.by дописывает имя зоны к значению, если оно
введено как относительное имя. С первого раза запись встала как
`...vercel-dns-016.com.eneca.by` и не работала.

Домен лучше адреса Vercel и его стоит взять до регистрации в Entra: домен
попадает в App ID URI, в messaging endpoint бота и в манифест Teams, поэтому
смена задним числом означает переделку всех трёх мест.

Что выяснено:

- Зона `eneca.by` обслуживается `ns1.hoster.by` / `ns2.hoster.by` — DNS правится
  в панели **hoster.by**. Апекс `eneca.by` указывает на `178.172.235.206`
  (корпоративный сайт), почта там же — посторонние записи не трогать.
- Домен `eneca.by` уже привязан к команде Vercel, но nameservers третьей стороны,
  то есть Vercel зоной не управляет. Wildcard `*.eneca.by` в зоне нет.
- `gamification.eneca.by` — CNAME на `500be54d73d66958.vercel-dns-016.com`.
  Значение уникально для каждого домена: копировать его для `trips` нельзя,
  Vercel выдаёт свой адрес вида `<хеш>.vercel-dns-0XX.com`.
- Сотрудник, заводивший `gamification.eneca.by`, уволился. Доступ в hoster.by
  искать в ИТ (там же корпоративный сайт) либо восстанавливать через поддержку
  hoster.by по договору.

Порядок: Vercel → проект → Settings → Domains → Add Domain → `trips.eneca.by`
(подтверждение владения не потребуется, домен уже в команде) → скопировать
показанное значение CNAME → в hoster.by добавить запись `CNAME` с именем `trips`
и этим значением, TTL по умолчанию. Vercel сам переключит статус на Valid
и выпустит сертификат.

### 3. Регистрация приложения в Entra ID

`entra.microsoft.com` → App registrations → New registration:

- Имя: `ЭНЭКА.Командировки`, тип — **Accounts in this organizational directory only**,
  Redirect URI не нужен.
- Записать **Application (client) ID** и **Directory (tenant) ID**.
- **Manage → Manifest**: `requestedAccessTokenVersion` = `2`.
  Делать **до** следующего шага, порядок принципиален. В тенанте, скорее всего,
  включена политика, запрещающая произвольные домены в Application ID URI
  («All newly added URIs must contain a tenant verified domain, tenant ID, or app ID»).
  Адрес на `vercel.app` под неё не подходит, но приложения с v2-токенами
  от этой политики освобождены. Если сначала задать URI, Entra его отклонит.
- **Expose an API → Application ID URI**: `api://<домен>/botid-<client-id>`
  (именно `botid-`, потому что в приложении есть и бот, и вкладка).
  Если URI всё равно отклонён — значит нужен корпоративный поддомен
  (он верифицирован в тенанте) либо исключение для приложения от админа.
- **Add a scope**: имя `access_as_user`, кто может соглашаться — **Admins and users**,
  отображаемые имена и описания заполнить по-русски.
- **Authorized client applications** — добавить оба ID, иначе SSO молча не работает:
  - `1fec8e78-bce4-4aaf-ab1b-5451cc387264` — Teams desktop и mobile
  - `5e3ce6c0-2b1f-4285-8d4b-75ee78787346` — Teams web
- **API permissions → Microsoft Graph**:
  - delegated: `openid`, `profile`, `email`, `offline_access`, `User.Read`
  - application: `User.Read.All` — для синхронизации справочника сотрудников
  - application: `TeamsAppInstallation.ReadWriteSelfForUser.All` — чтобы ставить
    приложение сотруднику, который боту не писал (см. ниже). Узкое: позволяет
    управлять только собственной установкой приложения
  - нажать **Grant admin consent**
- **Certificates & secrets** → новый client secret, записать значение сразу.

### 4. Регистрация бота

Бот заводится в **Teams Developer Portal** (`dev.teams.microsoft.com` → Tools →
Bot management). Портал сам создаёт регистрацию в Bot Framework, подписка Azure
для этого не нужна.

- **Configure → Delivery method**: HTTPS endpoint,
  адрес `https://trips.eneca.by/api/messages`
- **Channels**: включить Microsoft Teams
- **Client secrets**: создать, значение записать сразу

**12.11: решение — подписку Azure не запрашиваем.** В тенанте нет ни подписок,
ни платёжного аккаунта, то есть подписка — не клик администратора, а финансовый
процесс в организации. Ресурс Azure Bot (F0) бесплатен, но даёт только тип
приложения Single Tenant, управление в портале Azure и дополнительные каналы
связи — ничего из этого в этапе 1 не нужно. Заявка на подписку отозвана.

**Прецедент в организации.** Бот протоколов встреч **EnecaProtocolMeetBot**
(репозиторий `eneca-dev/Eneca_AI_bot`, работает на VPS за `ai-bot.eneca.work`)
отправляет протокол в чат Teams сам, без Azure. Схема в
`services/teams_sender.py` — та же, что у нас: ссылка на разговор сохраняется при
первом сообщении, затем токен по `client_credentials` со областью
`https://api.botframework.com/.default` и POST активности в Bot Connector.
Значит исходящая отправка в этом тенанте работает и подписка для неё не нужна.
Его регистрацию переиспользовать нельзя: messaging endpoint у регистрации один,
и он занят.

Если отправка сообщений ботом всё-таки упрётся в 401 — возвращаемся к ИТ с
конкретной ошибкой, а не с общей просьбой. Параметры ресурса на этот случай:
тип **Single Tenant**, существующая регистрация `eneca.trips`, SKU **F0**,
messaging endpoint `https://trips.eneca.by/api/messages`, канал Microsoft Teams.
Штатный путь перехода — кнопка **Migrate** в Bot Framework Portal: она создаёт
ресурс Azure Bot на той же регистрации.

Личную пробную подписку с кредитом 200 долларов не использовать: нужна привязка
личной карты, а продакшен-ресурс оказывается в подписке, которой организация не
управляет, и умирает вместе с ней через 12 месяцев.

Что нужно помнить про регистрацию из Developer Portal:

- Портал создаёт боту **свою** регистрацию приложения, идентификатор не совпадает
  с регистрацией вкладки. Поэтому в манифесте `botId` вынесен в отдельную
  переменную `NEXT_PUBLIC_TEAMS_BOT_ID`.
- Тип приложения залочен на **Multi tenant** и в портале не меняется, поэтому
  `MICROSOFT_APP_TYPE=MultiTenant`, а `MICROSOFT_APP_TENANT_ID` оставить пустым.
  Связка «бот multi-tenant, в конфигурации single-tenant» — типовая причина 401
  **при отправке** сообщений.
- Разрешений Microsoft Graph эта регистрация не запрашивает и согласия
  администратора не требует: сотрудник определяется по данным активности Teams.

Сами проактивные сообщения от способа регистрации не зависят: для отправки нужны
app id и secret, включённый канал Teams, сохранённый `conversation reference`
(поэтому приложение должно быть установлено сотруднику) и `serviceUrl` из
входящей активности. Bot Connector в цепочке есть всегда — Teams не доставляет
сообщения на наш сервер напрямую, и это не предмет выбора.

### 4а. Как бот пишет тому, кто ему не писал

Бот не может отправить сообщение в пустоту: пока приложение не установлено
сотруднику, разговора не существует и адреса для отправки нет. А участников
поездки добавляет АХО, и сами они боту не пишут — значит одного «сотрудник
написал первым» недостаточно.

Штатное решение — установить приложение программно:

```
POST https://graph.microsoft.com/v1.0/users/{entra-oid}/teamwork/installedApps
```

После установки Teams присылает боту событие установки с ссылкой на разговор, она
сохраняется в `teams_conversations`, дальше отправка обычная. Если у сотрудника
Teams запущен, установка происходит сразу.

Условия:

- разрешение приложения `TeamsAppInstallation.ReadWriteSelfForUser.All`;
- приложение должно быть **опубликовано в каталоге организации** — Graph ставит
  только то, что есть в каталоге. Это делает ИТ, и теперь это не удобство,
  а обязательное условие работы уведомлений.

Проще и надёжнее для запуска на всю компанию — **политика автоустановки**
приложения для группы сотрудников (тоже ИТ, однократно): тогда приложение стоит
у всех заранее и Graph нужен только для тех, кто в группу не попал.

Следствие для кода (И2): очередь `notifications` должна уметь состояние
«сначала поставить приложение, потом отправить». Схема не меняется — воркер
ставит приложение и переносит отправку через `send_after`.

Переход на Azure Bot, если он когда-нибудь понадобится: две переменные окружения
(`MICROSOFT_APP_*`, `NEXT_PUBLIC_TEAMS_BOT_ID`), пересборка манифеста и повторная
загрузка приложения в Teams. Код не меняется.

### 6. Проверка

Сначала локально, до деплоя — два скрипта, которые не выводят значения секретов:

```bash
node --env-file=.env.local scripts/check-env.mjs      # формат переменных
node --env-file=.env.local scripts/check-access.mjs   # работают ли секреты
```

`check-access.mjs` делает четыре читающих запроса: токен приложения в Entra и
`GET /users` в Graph (заодно видно, выдано ли согласие на `User.Read.All` и
приходят ли `jobTitle` и `department`), токен Bot Connector для бота,
чтение `employees` в Supabase, `getMe` в Telegram. **13.11: все четыре проходят.**

Переменные из `.env.example` внести в Vercel → Settings → Environment Variables
и передеплоить. Затем собрать и загрузить приложение в Teams:

```bash
cp .env.example .env.local   # те же значения локально, для сборки манифеста
npm run teams:package
Compress-Archive -Path teams/build/* -DestinationPath teams/build/eneca-transport.zip -Force
```

Teams → Apps → Manage your apps → Upload an app → Upload a custom app.

Критерии: вкладка показывает ФИО и Entra OID; бот в личном чате отвечает
«Связь есть»; Telegram-бот отвечает «Связь есть».

Плюс отдельная проверка, которую нельзя откладывать до И5: бот должен уметь
отправить сообщение **сам**, без входящей активности. На этом построены все
напоминания, и если отправка не работает, проект стоит.

```bash
# 1. Написать боту в личном чате. В ответе он покажет conversation id и service url.
# 2. Отправить сообщение от имени бота, не отвечая на входящее:
node --env-file=.env.local scripts/teams-proactive-test.mjs "<conversation id>" "<service url>"
```

Ожидаемый результат — сообщение «Проверка исходящей отправки» появляется в том же
чате. Ошибка 401 почти всегда означает рассогласование `MICROSOFT_APP_TYPE` с
типом регистрации бота, см. пункт 4.

## Задачи ИТ перед запуском

Долгие по срокам, поэтому запрашиваются заранее, а не в последнюю неделю.
Для пилота на нескольких людях хватит загрузки приложения себе, но для
запуска на компанию нужны оба пункта.

1. **Публикация приложения в каталоге организации.** Без неё Graph не может
   установить приложение сотруднику, а значит уведомления не дойдут до тех, кто
   боту не писал.
2. **Политика автоустановки** приложения для группы сотрудников. Тогда
   приложение стоит у всех заранее.
3. **Согласие администратора** на два разрешения приложения: `User.Read.All`
   (выдано 11.11) и `TeamsAppInstallation.ReadWriteSelfForUser.All`.
