# План реализации. Этап 1

Требования — в `docs/source/`. Этот файл только о порядке работ и статусе.
Целевой старт пилота — 30.11.2026. На 09.11 остаётся 15 рабочих дней.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Хранение данных (вариант А/Б, раздел 8) | **А.** Отдельный проект Supabase |
| Роли АХО / Рецепция / Финотдел | В своей БД (`employee_roles`), назначает АХО. Не App Roles в Entra — иначе каждое назначение роли блокируется заявкой в ИТ |
| Размещение | Повторяем схему геймификации: приложение на **Vercel** (команда `development-depts-projects`), воркер-планировщик — контейнером на **VPS** `2.56.125.26`, как `gamification-vps-scripts` |
| Публичный адрес | Постоянный адрес даёт Vercel, домен от ИТ для запуска не нужен. Задан одной переменной `NEXT_PUBLIC_APP_DOMAIN`. Корпоративный поддомен добавляется позже в Vercel → Domains: Vercel выдаёт готовую DNS-запись, её и передаём ИТ |
| Справочник сотрудников | Локальная копия из Microsoft Graph (application-разрешение `User.Read.All` + синхронизация воркером), без on-behalf-of |
| Регистрация в Entra | Одна регистрация на вкладку и бота. App ID URI — `api://<домен>/botid-<client-id>` |

## Стиль коммитов

Одна строка: `<область>: <что сделано>`. Область — номер инкремента (`И0`…`И9`)
либо `docs`, `infra`, `fix`. Со строчной буквы, без точки в конце, до 72 знаков.
Тело добавляется только когда в коммите несколько несвязанных изменений —
списком через `-`.

```
И0: каркас приложения, вход Entra ID, схема БД
И1: синхронизация сотрудников из Graph и роли
И2: заявка на поездку и бронь без водителя
docs: уточнён порядок регистрации в Entra
fix: буфер 10 минут считается от фактического возврата
```

## И0. Доступы и проверка связи — делается вручную

Это критический путь: пока не пройдено, ни бот, ни вкладка не проверяются.

### 1. Деплой на Vercel — делается первым, он даёт адрес

Адрес нужен раньше всего: он зашивается в App ID URI в Entra, в messaging endpoint
бота и в манифест Teams. Поэтому сначала деплой, потом регистрации.

1. Запушить код в `eneca-dev/eneca-transport`.
2. `vercel.com` → команда `development-depts-projects` → Add New → **Project** →
   Import Git Repository → `eneca-dev/eneca-transport`. Если репозиторий приватный,
   Vercel попросит доступ к организации на GitHub.
3. Framework Next.js определится сам, Root Directory — корень.
4. Deploy. Переменные окружения добавляются после — на первом деплое их ещё нет.

Проект в Vercel назван `eneca-trips`, production-адрес — `eneca-trips.vercel.app`.
Это значение `NEXT_PUBLIC_APP_DOMAIN`, без схемы и в нижнем регистре. Адреса
preview-деплоев не использовать: они меняются, и вход через Entra на них не работает.
Деплой запускается пушем в `main`.

### 1а. Корпоративный поддомен `trips.eneca.by` — если успеем до шага 3

Домен лучше адреса Vercel и его стоит взять до регистрации в Entra: домен
попадает в App ID URI, в messaging endpoint бота и в манифест Teams, поэтому
смена задним числом означает переделку всех трёх мест.

Что выяснено:

- Зона `eneca.by` обслуживается `ns1.hoster.by` / `ns2.hoster.by` — DNS правится
  в панели **hoster.by**. Апекс `eneca.by` указывает на `178.172.235.206`
  (корпоративный сайт), почта там же — посторонние записи не трогать.
- Домен `eneca.by` уже привязан к команде Vercel, но nameservers третьей стороны,
  то есть Vercel зоной не управляет. Wildcard `*.eneca.by` в зоне нет.
- `gamification.eneca.by` — CNAME на `500be54d73d66958.vercel-dns-016.com`.
  Значение уникально для каждого домена: копировать его для `trips` нельзя,
  Vercel выдаёт свой адрес вида `<хеш>.vercel-dns-0XX.com`.
- Сотрудник, заводивший `gamification.eneca.by`, уволился. Доступ в hoster.by
  искать в ИТ (там же корпоративный сайт) либо восстанавливать через поддержку
  hoster.by по договору.

Порядок: Vercel → проект → Settings → Domains → Add Domain → `trips.eneca.by`
(подтверждение владения не потребуется, домен уже в команде) → скопировать
показанное значение CNAME → в hoster.by добавить запись `CNAME` с именем `trips`
и этим значением, TTL по умолчанию. Vercel сам переключит статус на Valid
и выпустит сертификат.

### 2. Проверить права: Azure и Teams

- `portal.azure.com` → **Subscriptions**: есть ли хотя бы одна подписка.
  Без подписки ресурс Azure Bot не создать, и бота придётся запрашивать у ИТ.
- `admin.teams.microsoft.com` → **Teams apps** → **Setup policies** → Global:
  включён ли **Upload custom apps**. Без этого приложение не загрузить даже себе.

### 3. Регистрация приложения в Entra ID

`entra.microsoft.com` → App registrations → New registration:

- Имя: `ЭНЭКА.Командировки`, тип — **Accounts in this organizational directory only**,
  Redirect URI не нужен.
- Записать **Application (client) ID** и **Directory (tenant) ID**.
- **Manage → Manifest**: `requestedAccessTokenVersion` = `2`.
  Делать **до** следующего шага, порядок принципиален. В тенанте, скорее всего,
  включена политика, запрещающая произвольные домены в Application ID URI
  («All newly added URIs must contain a tenant verified domain, tenant ID, or app ID»).
  Адрес на `vercel.app` под неё не подходит, но приложения с v2-токенами
  от этой политики освобождены. Если сначала задать URI, Entra его отклонит.
- **Expose an API → Application ID URI**: `api://<домен>/botid-<client-id>`
  (именно `botid-`, потому что в приложении есть и бот, и вкладка).
  Если URI всё равно отклонён — значит нужен корпоративный поддомен
  (он верифицирован в тенанте) либо исключение для приложения от админа.
- **Add a scope**: имя `access_as_user`, кто может соглашаться — **Admins and users**,
  отображаемые имена и описания заполнить по-русски.
- **Authorized client applications** — добавить оба ID, иначе SSO молча не работает:
  - `1fec8e78-bce4-4aaf-ab1b-5451cc387264` — Teams desktop и mobile
  - `5e3ce6c0-2b1f-4285-8d4b-75ee78787346` — Teams web
- **API permissions → Microsoft Graph**:
  - delegated: `openid`, `profile`, `email`, `offline_access`, `User.Read`
  - application: `User.Read.All` — для синхронизации справочника сотрудников
  - нажать **Grant admin consent**
- **Certificates & secrets** → новый client secret, записать значение сразу.

### 4. Ресурс Azure Bot

`portal.azure.com` → Create resource → **Azure Bot**:

- Тип приложения — **Single Tenant**, использовать **существующую** регистрацию
  (вставить client id и tenant id), SKU — **F0** (бесплатный).
- **Configuration → Messaging endpoint**: `https://<домен>/api/messages`
- **Channels** → добавить **Microsoft Teams**.

### 5. Supabase и Telegram

- Создать новый проект Supabase, записать URL и `service_role` key,
  применить `supabase/migrations/0001_init.sql`.
- Создать бота у `@BotFather`, записать токен. Вебхук:
  `setWebhook` на `https://<домен>/api/telegram` с секретом из переменных окружения.

### 6. Проверка

Переменные из `.env.example` внести в Vercel → Settings → Environment Variables
и передеплоить. Затем собрать и загрузить приложение в Teams:

```bash
cp .env.example .env.local   # те же значения локально, для сборки манифеста
npm run teams:package
Compress-Archive -Path teams/build/* -DestinationPath teams/build/eneca-transport.zip -Force
```

Teams → Apps → Manage your apps → Upload an app → Upload a custom app.

Критерии: вкладка показывает ФИО и Entra OID; бот в личном чате отвечает
«Связь есть»; Telegram-бот отвечает «Связь есть».
